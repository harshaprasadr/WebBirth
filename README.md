# WebBirth — website

Editorial, motion-led company site for WebBirth (software development & digital products, Bengaluru).

**Stack:** React 19 · TypeScript · Vite 8 · Tailwind CSS 4 · GSAP 3 + ScrollTrigger + SplitText · Lenis · Three.js + React Three Fiber + Drei · Framer Motion · Lucide · React Router

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # type-check + production build → dist/
npm run preview
npm run images     # regenerate 640px variants after adding portfolio images
npm run sync:blog  # pull the latest posts + cover images from blog.webbirth.in
```

## Structure

```
src/
  animations/reveal.ts      declarative scroll reveals (data-reveal="lines|words|fade|clip|line") + parallax
  components/               one file per component (Navbar, CustomCursor, Hero, ProjectShowcase, …)
  data/projects.ts          portfolio — the only place to add/edit projects (imageSize/fit for non-square shots, url for live sites)
  data/showcase.ts          which project visuals are live-site captures vs mockup crops (images in public/projects/showcase/)
  data/posts.ts             generated by scripts/sync-blog.mjs — don't edit by hand
  data/site.ts              company facts, services, process, technologies, stats, testimonials
  hooks/                    media queries, pointer-follow, local time, document title
  lib/gsap.ts               plugin registration + shared matchMedia queries
  pages/                    Home, Project (/work/:slug), Legal (/privacy, /terms), 404
public/projects/showcase/   portfolio showcase captures (+ -640 variants)
public/blog/                blog cover images (generated)
public/brand/               logo mark; favicons + app icons live in public/
```

## Motion system

- **Lenis ↔ ScrollTrigger:** Lenis is driven by `gsap.ticker`, and `lenis.on('scroll', ScrollTrigger.update)` keeps them in sync (`SmoothScroll.tsx`).
- **Preloader** (`Preloader.tsx`): runs once per page load, about 2.3s. A black boot div in `index.html` covers the first paint. The logo and wordmark are revealed with a clip-path mask, an accent line draws 0→100%, then a two-layer curtain wipes up. Reduced motion gets a short fade.
- **WebGL** (`components/three/`): `HeroScene` (the logo in liquid glass — MeshTransmissionMaterial — refracting the headline; the DOM `<h1>` stays for accessibility and is repainted into a canvas texture at its exact position, then cross-faded out) and `MorphScene` (about 15k particles: galaxy → WebBirth logo sampled from `public/brand/webbirth-mark-lg.webp` → wave grid). Both are lazy-loaded *after* the preloader so shader compilation never stalls it. They pause off-screen and fall back to 2D or static visuals without WebGL. GSAP drives them through `sceneState` in `lib/webgl.ts`, with no React re-renders.
- **Page transitions:** `PageTransition.tsx` provides `go(to)` and `<TransitionLink>`. A curtain covers the screen (~420 ms), the route swaps, triggers refresh, and the curtain lifts (~480 ms). Same-page hashes just smooth-scroll.
- **Selected Work** (`WorkScenes.tsx`): sticky full-screen scenes that stack; real site captures scroll inside browser/phone frames.
- **Desktop only (≥1024px, motion allowed):** cursor-following previews, and the custom cursor (fine pointers only).
- **`prefers-reduced-motion`:** Lenis is off, the hero canvas renders one static frame, horizontal pinning becomes a vertical stack, and reveals become simple fades.

## Content rules

Everything shown is sourced. See the header comments in `src/data/site.ts` and `src/data/projects.ts`.

- Stats (500+ projects, 500+ clients, 15+ countries, founded 2020) come from WebBirth's LinkedIn company page.
- Testimonials live in `data/testimonials.ts` — real, publicly verifiable reviews only (Clutch, Trustpilot, Justdial + the 5.0 Google rating). Add new ones there verbatim; the home slider (`TestimonialsSection`) and the `/testimonials` page both read from it.
- Projects come from the live portfolio. Add `year`, `stack`, `deliverables` or a fuller `summary` once confirmed.

## Contact form

Set `VITE_CONTACT_ENDPOINT` (see `.env.example`) to any endpoint that accepts a JSON POST (Formspree, Basin, your own API). Without it, the form validates and then opens a pre-filled email to `info@webbirth.in`.

## Deploy

The `dist/` folder contains a `.htaccess` that rewrites all routes to `index.html` so client-side routes like `/work/girani` resolve on Apache (Hostinger).

## Brand assets

The logo mark (`public/brand/webbirth-mark.*`) and the favicons and app icons (`favicon-32/48.png`, `apple-touch-icon.png`, `icon-192/512.png`) were generated from the supplied logo PNG. Stray speckles were cleaned from its edges and it was trimmed. To replace the logo, regenerate these files from a transparent PNG at the same file names.

## Project visuals

`public/projects/showcase/` holds the images behind each project card. Eight projects use live captures of the client site, taken in Oct 2026 and checked to still match WebBirth's work: a full desktop page that scrolls on hover, plus a phone screen. The rest use the website screen cropped from the portfolio mockup, or the phone screen for the apps. To re-capture a live site, screenshot it at 1440px (full page) and 390px@2x, then keep the file names. Do not link Zodiac's old domain: it now redirects to a spam site.

## Suggestions for a good README

Every project is different, so consider which of these sections apply to yours. The sections used in the template are suggestions for most open source projects. Also keep in mind that while a README can be too long and detailed, too long is better than too short. If you think your README is too long, consider utilizing another form of documentation rather than cutting out information.

## Name
Choose a self-explaining name for your project.

## Description
Let people know what your project can do specifically. Provide context and add a link to any reference visitors might be unfamiliar with. A list of Features or a Background subsection can also be added here. If there are alternatives to your project, this is a good place to list differentiating factors.

## Badges
On some READMEs, you may see small images that convey metadata, such as whether or not all the tests are passing for the project. You can use Shields to add some to your README. Many services also have instructions for adding a badge.

## Visuals
Depending on what you are making, it can be a good idea to include screenshots or even a video (you'll frequently see GIFs rather than actual videos). Tools like ttygif can help, but check out Asciinema for a more sophisticated method.

## Installation
Within a particular ecosystem, there may be a common way of installing things, such as using Yarn, NuGet, or Homebrew. However, consider the possibility that whoever is reading your README is a novice and would like more guidance. Listing specific steps helps remove ambiguity and gets people to using your project as quickly as possible. If it only runs in a specific context like a particular programming language version or operating system or has dependencies that have to be installed manually, also add a Requirements subsection.

## Usage
Use examples liberally, and show the expected output if you can. It's helpful to have inline the smallest example of usage that you can demonstrate, while providing links to more sophisticated examples if they are too long to reasonably include in the README.

## Support
Tell people where they can go to for help. It can be any combination of an issue tracker, a chat room, an email address, etc.

## Roadmap
If you have ideas for releases in the future, it is a good idea to list them in the README.

## Contributing
State if you are open to contributions and what your requirements are for accepting them.

For people who want to make changes to your project, it's helpful to have some documentation on how to get started. Perhaps there is a script that they should run or some environment variables that they need to set. Make these steps explicit. These instructions could also be useful to your future self.

You can also document commands to lint the code or run tests. These steps help to ensure high code quality and reduce the likelihood that the changes inadvertently break something. Having instructions for running tests is especially helpful if it requires external setup, such as starting a Selenium server for testing in a browser.

## Authors and acknowledgment
Show your appreciation to those who have contributed to the project.

## License
For open source projects, say how it is licensed.

## Project status
If you have run out of energy or time for your project, put a note at the top of the README saying that development has slowed down or stopped completely. Someone may choose to fork your project or volunteer to step in as a maintainer or owner, allowing your project to keep going. You can also make an explicit request for maintainers.
